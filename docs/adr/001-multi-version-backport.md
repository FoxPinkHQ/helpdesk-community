# ADR-001: Multi-Version Backport Strategy

**Date**: 2026-07-13
**Status**: Accepted
**Scope**: All FoxPink modules

## Context

Single-version (19-only) limits market reach. Odoo users on 14–18 are a large installed base. Multi-version support is a key differentiator on Odoo Apps Store.

## Decision

- **Source of truth**: Odoo 19 (all feature development happens here)
- **Backport pipeline**: 19 → 18 → 17 → 16 → 15 → 14 (sequential, not parallel)
- **Git branches**: `19.0` (primary dev), `18.0`, `17.0`, `16.0`, `15.0`, `14.0` (maintenance)
- **Release gate**: All 6 versions must pass before ANY version is published
- Each maintenance branch = artifact **generated by the Compatibility Layer**, not hand-patched

### Phase 1.5 (revised): Compatibility-Layer-first

Backporting is NOT done by manually editing each branch. Instead:

1. **Extract, don't edit.** Use the golden 19.0 module to discover every 19↔N
   difference and record each as a **compatibility rule** (see
   `docs/compatibility/`). The "trial backport" produces *rules*, not code.
2. **Knowledge base** (publisher-wide, reused by all 40–50 modules):
   - `docs/compatibility/MATRIX.md` — component × version support grid
   - `docs/compatibility/RULES.md` — structured transforms keyed by compiler pass
   - `docs/compatibility/BOUNDARIES.md` — which rules fire per version boundary
3. **Compiler owns adaptation.** Rules feed the Version Compatibility Layer
   (passes: `ManifestPass`, `TrackingPass`, `ViewPass`, `ReportPass`, `AssetPass`).
   No module contains `if target == 17` branching.
4. **Promotion gate.** A rule is `verify` until the generated artifact installs +
   passes tests on that series' Docker instance; only then it becomes `stable`.

Rationale: the durable FoxPink advantage is a compiler that understands Odoo
version differences. Each new supported series (e.g. Odoo 20) then extends the
layer instead of re-patching every module.

## Consequences

- Feature development only on 19. Backports are mechanical (API adapters, XML transforms).
- Bug fixes: fix on 19, then cherry-pick down the pipeline.
- Compiler must have a **Version Compatibility Layer** producing artifacts per target.
- **One commit → six artifacts**: CI pipeline builds 6 ZIPs per module.
- Backport 19→14 should take ≤1 week per module (KPI).
- Code variance across versions must be <5% (KPI).

## Two lifecycles (do not overload the word "Release")

FoxPink runs **two independent lifecycles**. They must never share the term
"Release" unqualified.

### Engineering Lifecycle (internal)
- Purpose: lock history, mark milestones, enable rollback, anchor regression
  points, and trace *when* a rule/fix was introduced.
- Cadence: as often as needed on the `19.0` golden branch.
- Artifacts: git commit + tag + **GitHub Release marked "Engineering"**.
- Versions: `19.0.1.0.0`, `19.0.1.0.1`, `19.0.2.0.0`, …
- **Does NOT publish to the Odoo Apps Store.**
- Gate: golden installs + tests green on Docker 19.

### Market Lifecycle (customer-facing)
- Purpose: the release that appears on the Odoo Apps Store.
- Gate: the multi-version Definition of Done below is fully green (14–19).
- Artifacts: six simultaneously-published series builds.
- Versions (published together):
  `14.0.1.0.0 · 15.0.1.0.0 · 16.0.1.0.0 · 17.0.1.0.0 · 18.0.1.0.0 · 19.0.<n>`

```
Engineering Milestone  ──▶  Compatibility Verified (14–19)  ──▶  Market Release
```

### Definition of Done — Market gate

| Version | Install | Tests | Package |
|---------|:-------:|:-----:|:-------:|
| 19      | ✅      | ✅    | ✅      |
| 18      | ⬜      | ⬜    | ⬜      |
| 17      | ⬜      | ⬜    | ⬜      |
| 16      | ⬜      | ⬜    | ⬜      |
| 15      | ⬜      | ⬜    | ⬜      |
| 14      | ⬜      | ⬜    | ⬜      |

A **Market Release** happens only when the full table is green.
An **Engineering Release** needs only the 19 row.

### Rule provenance (traceability)

Every rule that reaches `Stable` records:
- **Introduced In** — the engineering milestone that first shipped it
- **Verified In** — the environment that proved it (source read / Docker series)
- **Last Validated** — date of the most recent green run

So when a future series (e.g. Odoo 20) breaks a rule, the Compiler knows exactly
which milestone introduced it and when it was last validated.

## Alternatives Considered

- **Parallel development**: Rejected — 6x bug-fix surface.
- **Single branch with compat layer**: Rejected — too complex for Odoo XML/security differences.
